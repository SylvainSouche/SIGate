# SIGate — Development Workflow

Companion to `qgis_plugin_spec.md` (what to build). This document is how we build it: coding rules, then a step-by-step sequence with a validation checkpoint after each step, on one side or the other, before moving to the next.

---

## Step 0 — Coding rules

**Compatibility target**: Python 3.9+ syntax, conservatively — `Optional[X]`/`Union[X, Y]` from `typing` rather than `X | Y` shorthand (3.10+), no `match` statements. QGIS bundles whatever Python its own installer ships, varies by version/platform; write for the older end of the currently-supported range rather than assume the newest.

**Naming, GIS-oriented over computer-science-oriented**: domain terms win even where a generic term is the "usual" Pythonic choice — `typename`/`bbox`/`tilematrixset`/`dalle`, not `item_type`/`bounds`/`grid`/`chunk`. Variable names state their usage, not just their type or shape (`destination_target`, not `dst`; `expected_total_features`, not `n`).

**`sigate` prefix — only where global uniqueness is genuinely load-bearing**:
- `providerKey()` strings: `sigate_atom`, `sigate_wfs`, `sigate_wmts` — lowercase, underscore, matching QGIS core's own provider-key convention (`"postgres"`, `"wms"`, `"ogr"`).
- `QgsSettings` namespace: `SIGate/...` (the product name, not an abbreviation) for the legitimate small scalar settings (size-warning threshold, detected 7z path, UI locale).
- Nowhere else — Python's own module/package namespace already disambiguates our classes and functions (`sigate.gateways.wfs.WfsGateway`, not `SigWfsGateway`); a prefix there would be noise, not signal.

**Case convention**: snake_case for everything we own (functions, our own methods, variables, modules). camelCase *only* where overriding a Qt/QGIS-mandated method name (`initGui`, `createDataSourceWidget`, etc.) — those aren't a style choice, they're fixed by the API we're implementing against.

**Code style**: clear and plain over clever. No obfuscating one-liners, no cute construct chosen for brevity over readability, even where the clever version is shorter. Standard, boring, best-practice patterns by default.

**Documentation**: every module and function documents what it does and why. Comments describe the code and its technical rationale — protocol quirks, why a particular check exists, what a real server is known to do — never the development history of how a decision was reached. No references to "this session," prior conversation, or the exploratory tools this codebase was ported from; the shipped code stands on its own, as if written fresh, with no implied prior context the reader doesn't have.

**No hardcoded protocol/service strings scattered through function bodies**: parameter names, header values, namespace URIs, element names, and similar protocol constants are named module-level constants, grouped in a shared constants module where more than one gateway type would otherwise repeat the same value (e.g. `gateways/ogc_constants.py` for the SERVICE/VERSION/REQUEST pattern common to WFS/WMS/WMTS/WCS). A function body should read as domain logic, not a mix of logic and inline magic strings.

**Error handling**: typed exceptions where a caller needs to distinguish failure modes (the pattern `WfsServerException` already established) — never a silent `None`/empty-result return that could be mistaken for "genuinely no data." Two-tier reporting: a clear, actionable message surfaced to the user in the UI; full diagnostic detail (raw response body, stack trace, the actual request URL) always logged to console/`QgsMessageLog`, never only shown to the user and never silently swallowed.

**Logging**: `QgsMessageLog`/`iface.messageBar()` inside `ui/` — never a bare `print()`, which is invisible to a normal QGIS user. Pure-Python modules (`gateways/`, `download/`, `sources/`) stay logging-agnostic — return results or raise, let the caller decide how to surface it, same separation the standalone tools already have.

**Formatting/linting**: `black` (or `ruff format`) + `ruff`.

**Type hints**: on all new function signatures in the pure-Python layer (`gateways/`, `download/`, `sources/`) — cheap, and exactly where hints pay for themselves in an editor. Looser in `ui/`, where Qt's own typing is already verbose.

**License**: BSD-3-Clause. Compatible with the QGIS repository's GPLv2-or-later requirement (confirmed: 2-Clause and 3-Clause BSD are GPL-compatible per FSF; the original 4-Clause BSD, with its advertising clause, is the one variant that isn't — not the one we're using), while staying more permissive downstream than GPL's copyleft would be. Every source file carries the standard BSD-3-Clause header; a `LICENSE` file at the repo root.

**Network transport — a real constraint from the QGIS plugin repository's own recommendations, not just a style preference**: plugins should use `QgsNetworkAccessManager` rather than `urllib`/`requests` directly, since those bypass QGIS's own proxy configuration. But `gateways/` was deliberately built pure-Python specifically so it's testable without a live QGIS — wiring `QgsNetworkAccessManager` in directly would break that. Resolution: `gateways/` takes an **injected fetch function** (a plain callable: URL in, bytes out) rather than importing any HTTP client itself. The real plugin wires in a `QgsNetworkAccessManager`-backed implementation at `ui/` construction time; `pytest` wires in a mock. Same separation of concerns already used throughout this session's standalone tools, just formalized as an explicit injection point instead of a module-level function to monkeypatch.

**Testing**: `pytest`, targeting the pure-Python layer only, using the same mocked/logic-testing technique already proven this session (network calls and, where relevant, Qt objects mocked out — no live server, no live QGIS needed to run the suite). `ui/` isn't unit-tested this way; it's covered by the manual validation checkpoints below instead.

**Versioning during this pre-release development phase**: `metadata.txt`'s `version` field follows `0.0.#`, incremented by one on every packaged build handed off (not per code change - one bump per zip actually delivered) — requested directly, current count starts at 17. Not semantic versioning; this is a plain build counter for a plugin that hasn't had a real release yet. Switch to actual semantic versioning once there's a first real, tagged release to version against. The delivered archive itself is named to match: `sigate-0.0.#.zip`, not a bare `sigate.zip` - requested directly, so consecutive deliveries are distinguishable by filename alone.

**Repository hygiene** (per the QGIS plugin repository's own stated requirements — worth following from the first commit, not cleaned up retroactively before submission): no generated files committed (`ui_*.py`, `resources_rc.py`, compiled `.qm` translation files — these are build artifacts, regenerated from source), no `.git`/`__pycache__`/`__MACOSX`/other hidden directories in the distributed package, `README.md` and `LICENSE` present at the repo root, comments in English throughout. The zipped package uploaded to the plugin repository must match the `repository` URL declared in `metadata.txt` exactly.

**External code review — applied by principle, not by literal diff.** A code review is a snapshot against whatever the codebase looked like at the moment it ran; by the time it's read, real, ongoing development means some of its line-level detail may no longer match the current code, or some reviewed files may have grown well past what was reviewed, or new files may exist that were never seen at all. None of that makes the review's *findings* wrong — a category of issue found in file A is worth checking for in file B too, even if B was never reviewed, and a specific line-numbered comment should be read as "this class of problem exists here," not "fix exactly this line." Applying a review means: extract each issue category into a general, repeatable check; sweep the *entire current codebase* against each check, not just the files the review happened to cover; and treat every category as a permanent standard to hold future code to, not a one-time cleanup. The standing categories from the first full review (kept here so future code is written to the same bar from the start, not corrected after the fact):
1. No development-history narrative in docstrings/comments (the existing Documentation rule above) — a regression-preventing note about a *current* constraint may stay; a sentence that only explains how a decision was reached historically should not.
2. Every public function/method has a parameter contract: what's accepted, what happens on `None`/empty/wrong input, what it raises, what side effects it has.
3. Every `except Exception` site logs full diagnostic detail (the real exception, not just its string form) via `QgsMessageLog` in `ui/`, in addition to whatever user-facing message is shown — never swallowed silently, never diagnostic-detail-only-in-the-user-facing-string.
4. Public functions in `download/`, `gateways/`, `sources/` validate their preconditions at the top and raise a typed, informative error, rather than letting an invalid input fail deep inside with a less useful error.
5. Subprocess calls (`7z`, `gdalbuildvrt`, `gdaladdo`, `gdal raster clip`, `gdal_translate`) pass an explicit `timeout=` and surface `stderr` in the failure message, not just `CalledProcessError`'s own text.
6. Type hints on every public function/method signature, including in `ui/` (previously looser there; tightened after review).

When history-narrative is trimmed from a docstring/comment, the substance isn't discarded: if it maps to a dated fix already in the "Post-ship fixes" log below, nothing further is needed (the trim alone is correct). If it doesn't — evergreen design rationale for a module that was never tied to one specific dated fix — it moves to `docs/module_notes/<same path as the source file>.md` (e.g. rationale trimmed from `ui/wfs_widget.py` goes to `docs/module_notes/ui/wfs_widget.md`), so the reasoning is preserved somewhere a maintainer would actually think to look, rather than deleted outright or left cluttering the live source.

## Development steps

Each step ends with a validation checkpoint — stated explicitly as either something verifiable without a live QGIS install (compiles, passes its test suite, logic-checked against mocked data — checkable on my side, the same way this session's standalone-tool code was validated) or something that genuinely needs a real QGIS install to confirm (checkable only on your side).

### Step 1 — Pure-Python gateway layer ✅ DONE
Port `gis.py`'s Atom logic and `atom_explorer_gui.py`'s WFS logic (capabilities, `GetFeature`, CSV/GML parsing, `CQL_FILTER` search, exception detection) into `gateways/atom.py` and `gateways/wfs.py`, unchanged in behavior — this is a relocation, not a rewrite, since none of it touches Tkinter.
**Validation (my side) — passed**: 13 tests in `tests/test_gateways.py`, including the critical server-page-capping regression test from this session's WFS filter work. `gateways/base.py` added the capability declaration and the injected-fetch-function transport point (Step 0's network-transport rule). Lint-clean (`ruff check`), formatted (`ruff format`), no 3.10+ syntax.

### Step 2 — `sources/` registry ✅ DONE
`seed.py` (IGN populated, as Python dataclasses) + `store.py` (load/merge seed + user JSON override, save-new-entry path).
**Validation (my side) — passed**: 9 tests in `tests/test_sources.py`. One real modeling gap caught and fixed during this step: the initial `SourceConfig.gateway()` lookup only returned one match per gateway type, which would have silently dropped IGN's second WMTS endpoint (it genuinely has two — public/no-auth and private/apikey) — added `gateways_of_type()` to return all matches, with a test specifically confirming both endpoints survive.

### Step 3 — `download/` pipeline core ✅ DONE
`targets.py`, `archive.py` (incl. split-7z grouping), `integrity.py`, `extraction_structure.py`, `mosaic.py`.
**Validation (my side) — passed, and went further than planned**: a real `p7zip-full` binary was installed in this environment specifically to test the archive module against genuine `.zip`/`.tar.gz`/`.7z` files rather than only mocked data — including a real multi-part split `.7z.001`/`.7z.002`/... archive, extracted and verified byte-exact via MD5 starting from either its first or its last part. This caught a real bug before it shipped: `7z l -slt`'s output begins with an archive-level header block that itself contains a misleading `Path = ` line (naming the archive file, not a member) — the initial parser implementation would have surfaced that as a phantom member. Fixed by locating the real `----------` separator the format uses and parsing only what follows it. `extraction_structure.py` was tested against the two real archive layouts (numbered role folders directly at archive root, and nested one level deeper under a product subfolder) confirmed earlier in this project. 40 new tests, 62 total across the whole codebase.

### Step 4 — Plugin registration skeleton ✅ DONE
`plugin.py`, `metadata.txt`, `ui/wmts_wms_provider.py`/`ui/wmts_wms_widget.py` — the WM(T)S browse-and-handoff tab, plus `gateways/wmts_wms.py` (pure URI-building logic for QGIS's native "wms" provider, which handles both WMS and WMTS through the same connection-string format).
**Validation (my side) — passed, full live end-to-end**: registration, lookup by key, `createSelectionWidget()`, widget population from the real seed source config, simulated selection and "Add to map" click correctly emitting the real `addRasterLayer(uri, name, provider)` signal (its exact name and signature confirmed by introspecting `QgsAbstractDataSourceWidget`'s meta-object live, rather than assumed by symmetry with the one signal already seen in QGIS's own source), and clean `unload()`. One real bug caught by this test and fixed before it shipped: the widget's URI builder silently defaulted to Web Mercator (`EPSG:3857`) for a layer confirmed to require Lambert-93 (`EPSG:2154`) — the same class of CRS mismatch that affected the standalone scripts earlier in this project. Fixed by adding an explicit CRS field to the source config rather than relying on any default, with a regression test added. Auth-gated layers (the private, apikey WMTS endpoint) are deliberately excluded from this tab for now, since QGIS's native WMS/WMTS provider's support for a custom authentication header has not yet been established — noted as a new open item below.

### Step 5 — Bulk Listing tab UI ✅ DONE (Atom only — FTP/STAC gateways don't exist yet, so only the Atom-backed source is wired in; the tab's design accommodates adding them later without changing this wiring)
`download/pipeline.py` (orchestration: already-downloaded check, size/free-space checks, download with byte-count/MD5 integrity, archive-vs-simple-file branch, extraction, simple-file placement), `ui/target_picker.py` (shared central-repo/destination widget), `ui/bulk_listing_widget.py` + `ui/bulk_listing_provider.py` (the actual tab, wiring the Atom gateway and the full pipeline together), plus a new `atom.resolve_downloadable_files` for the case where a selected entry resolves to more than one physical file.
**Validation (my side) — passed, full live end-to-end, and caught two real bugs before they shipped**:
1. The widget initially called `atom.fetch_page`/`resolve_downloadable_files` with no way to inject a test transport — meaning it could only be tested against the real network, which this environment can't reach. Fixed by adding the same `fetch`/`download_fn` injection points used throughout the rest of the codebase, directly to the widget's constructor.
2. A genuine extraction bug: the code assumed extracted files land flattened at the destination root (`destination / Path(member).name`), but real extraction preserves each archive member's full internal path (`destination / member_path`). Caught by a real end-to-end test using an actual in-memory zip archive built with the confirmed numbered-folder structure; fixed, and kept as a permanent regression test.

Live-tested: provider registration (now 2 providers alongside WM(T)S's 1), Atom navigation via injected feeds, a simple-file download placed and added as a raster layer, an archive download correctly integrity-checked, extracted with only its DONNEES-role member (metadata excluded), and added as a layer at the correct nested path, and a deliberately-mismatched byte count correctly rejected with the bad file deleted and no layer added. 96 tests total across the whole project.

Still needs your side: an actual download against the real IGN server over a real network connection — everything here is proven against realistic injected data, not the live service itself.

### Step 6 — WFS tab UI ✅ DONE
`ui/wfs_widget.py` + `ui/wfs_provider.py`: capabilities browse with a live layer-name filter, an optional attribute filter, and a direct handoff to QGIS's native WFS provider via `addVectorLayer` — no feature fetching of SIGate's own.
**Validation (my side) — passed, full live end-to-end, with real findings along the way**:
1. QGIS's native WFS connection-string format was verified against two independent real-world examples (found via search, both actual `dataProvider().uri()` output from real QGIS sessions) plus the official `QgsVectorLayer` documentation — it is a space-separated `key='value'` format, genuinely different from WMS/WMTS's plain URL-query-string format used in Step 4. The native provider key is also case-sensitive and differently-cased: `"WFS"`, not the lowercase `"wms"`.
2. `QgsProviderRegistry.decodeUri`/`encodeUri` for the `"WFS"` provider returned empty in this QGIS build — that verification path was a dead end, confirmed by direct test rather than assumed to work.
3. `QgsDataSourceUri.setParam()` was confirmed (via a live round-trip test) to correctly escape a filter value containing an embedded single quote — this is why the URI-building logic lives in the Qt-dependent `ui/` layer rather than the pure-Python `gateways/wfs.py`, unlike the WMS/WMTS case: hand-formatting this string ourselves would have risked exactly the kind of escaping bug this test specifically checked for.
4. Documented, not yet fully resolved: QGIS's native "filter" parameter takes a QGIS expression (which QGIS itself translates to OGC XML server-side), not the CQL_FILTER vendor syntax `gateways.wfs.build_field_search_cql` produces for direct HTTP requests. Basic field/value expressions use compatible syntax between the two for the common case, so that function is reused as-is here, but this is a syntax overlap, not a guaranteed general equivalence — noted as an open item below.

One stale test caught and fixed along the way: an earlier Step 5 test asserted the plugin registers exactly 2 providers, which was correct at the time but became wrong the moment this step added a third — a good, ordinary example of tests needing to grow with the code rather than a real bug. 103 tests total across the whole project.

### Step 7 — Settings dialog, i18n scaffolding ✅ DONE
`ui/settings.py` (typed get/set wrappers around `QgsSettings`), `ui/settings_dialog.py` (size-warning threshold, 7-Zip path override, with Browse/Auto-detect), and a real `.ts` translation file generated from the actual source.
**Validation (my side) — passed, and caught two real bugs**:
1. The planned mechanical `tr()`-discipline check was done properly with an AST parse (not a regex — an earlier regex attempt produced unreliable false positives, confirmed by cross-checking against a manual line-by-line read) across every file in `ui/`. Found exactly one real violation (a bare `QLabel("=")`), fixed it, and turned the same AST scan into a permanent test (`test_tr_discipline.py`) so future steps get checked automatically rather than needing another manual pass.
2. A genuine bug in `ui/settings.py`'s first draft: storing the size-warning threshold via `QgsSettings`' `type=int` coercion silently wraps around at 2 GB (`2**31`, one past the max signed 32-bit int) — a value entirely realistic for this exact setting, given the sizes seen throughout this whole project. Caught immediately by the first test written, before it could ship; fixed by storing the value as a string and parsing in Python, sidestepping Qt's 32-bit int coercion entirely.

The settings dialog is wired to actually change the Bulk Listing tab's behavior, not just display values decoratively — confirmed by a live test that a saved 7-Zip path override is used instead of auto-detection.

i18n toolchain confirmed working end to end with the real, standard tools (not simulated): `pylupdate5` (from the `pyqt5-dev-tools` package) correctly extracted all 63 `tr()`-wrapped strings across all 5 widget classes into a real `.ts` file; `lrelease` was used to confirm it compiles to a valid `.qm` (Qt Translation file, confirmed via `file`), though the `.qm` itself is a build artifact and isn't tracked in the repository, per the same hygiene rule established in Step 0.

Not built this step, deferred per the workflow's own original scope: source-config management (add/edit a country's gateway configuration) through the settings dialog — still config-file-only for now, no UI for it.

### Step 8 — Second country (proves the abstraction actually generalizes)
Add one non-IGN source config (candidate: Spain's CNIG, flagged earlier as structurally close to IGN's Atom shape) with zero changes to `gateways/`/`download/` — only a new `sources/` entry.
**Validation (your side)**: real download against the second country, using only config, no new gateway code — the actual test of whether §2's "three tabs, not five" factorization claim holds up in practice, not just in the fixtures from Step 3.

`metadata.txt` filled in for real: `homepage` (usage docs or repo README/wiki), `repository` (public source, no zipped files inside it), `tracker` (issue tracker), `license=BSD-3-Clause`, a short English `description`, and an explicit statement of the optional `.7z`-support dependency (external tool, not a bundled Python package, per §4.2/§8 — still needs stating plainly per the repository's own "external dependency must be clearly stated" rule). Package size checked against the repository's 25MB cap. Publishing itself needs an OSGeo ID for whoever uploads it — not a build blocker, but worth having ready before this step, not discovered at it.
**Validation (your side)**: a dry-run zip built and checked against the repository's stated requirements (§0's hygiene rules, size cap, metadata completeness) before actual upload.

## Post-ship fixes

Bugs found and fixed after the initial 9 steps and first packaged archive, logged here rather than folded silently back into the step that originally introduced them.

- **`build_qgis_wms_uri()` over-encoded the connection string, breaking "Add to map" entirely** — reported directly via a side-by-side comparison against a real, working connection string QGIS's own native "Add WMS/WMTS Layer" dialog produced for the identical layer. The bug: `quote(value, safe='')` was used everywhere, encoding literally every special character in every value — including `:` and `/` in simple values like `EPSG:3857` and `image/jpeg`, and, more seriously, the scheme/host/path portion of the embedded `url=` parameter's own URL. QGIS's real convention, confirmed by direct comparison, only escapes characters that would actually conflict with the outer `key=value&key=value` structure — literal `=` and `&` within a value — while leaving `:`, `/`, `?` as plain characters throughout. Fixed by changing to `quote(value, safe=':/?')`, confirmed to reproduce the real working string exactly, character for character. A dedicated regression test now checks the exact reported strings directly, plus explicitly asserts `%3A`/`%2F` never appear in the output at all.

- **Added a real package icon**: `icon=icon.png` was removed from `metadata.txt` back in Step 4/packaging, since no icon file existed at the time and shipping a broken reference was worse than none. A real 64×64 icon was provided and added at `sigate/icon.png`, `metadata.txt` updated accordingly, and all three `QgsSourceSelectProvider.icon()` methods (previously all returning an empty placeholder `QIcon()`) wired to a new shared `ui/icons.py` helper that resolves the icon's path relative to its own module location, rather than duplicating that path-resolution logic three times. Confirmed with tests that the icon file exists at the expected path and that all three providers return a genuinely non-null icon.

- **The WM(T)S tab only ever showed a single hardcoded layer per connection, never the real list of layers a server actually serves** — a genuinely serious bug, reported directly by real use rather than found through testing. `gateways/wmts_wms.py` had never implemented any GetCapabilities fetching or parsing at all — it was a pure URI builder from Step 4 onward, and the widget's layer list was populated entirely from a single `example_layer` string hand-typed into `sources/seed.py` to prove the Data Source Manager registration mechanism worked. That placeholder was never replaced with genuine capabilities parsing, so the tab showed exactly one fake "layer" regardless of what the real server actually offered.

  Fixed by adding real `wmts_get_capabilities()` to the gateway (namespace-agnostic parsing of a WMTS `Contents` section — every `Layer`, with its declared styles/formats/tile-matrix-set links, plus every top-level `TileMatrixSet` definition with its declared CRS) and rewriting the widget to fetch and list every layer a connection's server genuinely returns, with a filter box added given a real capabilities document can list far more layers than the one example ever suggested. The earlier CRS-correctness fix (Lambert-93 vs. Web Mercator, from Step 4) is now a *general*, structurally-guaranteed property rather than a value that happened to be hardcoded correctly for one specific layer — the CRS is cross-referenced from the server's own declared tile-matrix-set definitions for whichever layer is actually selected, confirmed with two separate regression tests using two different layers on two different tile matrix sets. The now-meaningless `example_layer`/`example_tilematrixset`/`example_style`/`example_crs` keys were removed from `sources/seed.py` entirely, along with the one test that had been asserting against them. 19 tests total across the gateway and widget layers now cover this (up from 4 + 4), including a defensive test confirming a capabilities-fetch failure for one gateway doesn't take down the whole tab.

- **WFS's attribute filter replaced entirely, after a multi-turn design study**: the original two-box `field = value` filter (built during the file-index-download fix) was replaced with a genuine, custom-built expression editor (`ui/expression_builder.py`) after confirming no existing QGIS widget was a real fit — `QgsExpressionBuilderWidget` produces QGIS-expression syntax (a different language from CQL), `QgsQueryBuilder` requires a real layer and is a generic database-query tool, and the actual native widget QGIS's own WFS "Build Query" uses (`QgsSQLComposerDialog`) is confirmed not exposed to Python at all. The new widget uses `QgsCodeEditorSQL` (real, QScintilla-based, genuine SQL syntax highlighting and autocompletion already built in — `setFieldNames()`/`setExtraKeywords()` confirmed as the correct, current APIs after an initial test with `QgsExpressionBuilderWidget.loadFieldsAndValues()` turned out to be a confirmed no-op since QGIS 3.14, not something that silently worked as an early test seemed to suggest). Sample/all value browsing uses a genuine in-memory `QgsVectorLayer` (geometry type `"None"`) built from whatever page was last queried, since `QgsVectorLayer.uniqueValues()` is the real, current mechanism for this. Two special tokens, `$geom` and `@map_extent`, are handled as plain literal text substitution rather than real QGIS expression evaluation — confirmed the safer choice after finding a real QGIS issue showing `@map_extent` doesn't resolve inside a comparable SQL execution context (QGIS's own "virtual layer" SQL).

  Integrated into `wfs_widget.py` in place of the old boxes: the widget's fields/values panels refresh automatically after each successful "Query features" call (using the real returned field names and rows, with the geometry field guessed via a small heuristic checking common column names like `wkt_geom`), and clear automatically when a different feature type is selected, so stale field names from a previous type are never left displayed. The resolved expression (tokens substituted) feeds both "Add to map" and "Query features" identically. `get_canvas_extent_wkt` is wired to `None` for now — `@map_extent` is left as a literal, unsubstituted token if typed, since none of SIGate's tab widgets currently have access to `iface`/the real map canvas at all; wiring that through the whole plugin construction chain is a separate, larger piece of work than this integration covered. 21 tests total in the WFS suite now (up from 16), including direct confirmation that a real query's field names and sample values reach the editor correctly.

- **Added a `Makefile`** (sibling of `sigate/`, not inside it — caught a real placement bug on the first attempt, since its paths assumed sitting outside the plugin folder) with `test`/`lint`/`format`/`i18n`/`package`/`verify`/`clean`/`profile-path` targets, replacing the same ad-hoc sequence of manual commands that had been run by hand after every change up to this point. `verify` in particular formalizes the "rebuild, extract fresh, re-test against the actual zip" cycle already being done manually.

- **Bulk Listing tab had no page navigation** (found via direct use of the packaged plugin, not automated testing): `_load()` only ever fetched page 1 of an Atom listing, with no way to reach further pages if a folder had more entries than one page's worth (IGN's page size is 50). Fixed by threading a `page` parameter through `_load()`, adding Prev/Next buttons and a page-count label driven by the feed's own reported `pagecount`/`totalentries`, and confirming navigating into a genuinely new URL correctly resets back to page 1 rather than carrying over whatever page a previous listing happened to be on. Covered by a new test with a real two-page fake feed. `docs/test_scenarios.md`'s TC3 updated to include a manual pagination check.

- **No filter capability in the Bulk Listing tab at all** (found via direct use): the original standalone Tkinter tool this plugin was built from had both a live current-page filter and a "filter across all pages" feature, neither of which was ever ported into the actual shipped widget during Step 5 — a real capability gap, not a bug in existing code. Fixed by adding a filter row (live current-page filtering with no extra fetch, plus a "Filter (all pages)" button using `atom.fetch_all_pages` with the same large-listing confirmation the underlying gateway already supported) and a `filtered_mode` flag that disables page navigation while an all-pages filter is active, consistent with how the original standalone tool handled the same state. Covered by two new tests: one confirming current-page filtering triggers no extra network fetch, one confirming an all-pages filter correctly finds an entry sitting on a page beyond what's currently displayed.

- **Central repository/destination paths were never remembered between sessions** (found via direct use): `download/targets.py` has had a full named-bookmark persistence mechanism, built and tested, since Step 3 — but `ui/target_picker.py` never actually called into it, or into any persistence at all. Fixed with a simpler, more direct mechanism than the full bookmark system: two new scalar `QgsSettings` values (`ui/settings.py`) for the single most-recently-used central-repo and destination paths, loaded automatically when `TargetPicker` is constructed and saved on every edit. - **The private gateway's own layers still didn't appear after the authcfg fix above** — reported directly, immediately after that fix shipped ("i only have one ign source and that is the opendata one, not the gated one"). - **"Load some"/"Load all" did nothing** — reported directly, immediately after the fields-populate fix above ("select a field name and click load some or load all, nothing happens"). Not reproducible directly in this environment (no live QGIS available here), so this was investigated by static inspection rather than a live repro, and addressed on two fronts: fixing the most plausible concrete root cause found on inspection, and - independently of whether that was the actual cause - making every way this path could come up silently empty visible instead, so a wrong diagnosis here would still leave a diagnosable state rather than a dead end.

  **Most plausible root cause found and fixed**: `build_memory_layer_from_rows` (the in-memory sample layer `_load_values` looks values up against) built its field schema by encoding field names into the memory provider's own connection-string syntax (`"field=NAME:TYPE&field=..."`) - a syntax with no escaping mechanism for `&` or `=`, both legal characters in a real attribute name and also that syntax's own delimiters. A field name containing either would silently corrupt the resulting layer's actual schema, so `fields().lookupField(name)` - the exact call `_load_values` makes to find the field the user selected - would fail to find it (or find the wrong thing), while the *fields list itself* (built directly from `fieldnames`, not from the corrupted layer) would still display correctly - matching the reported symptom exactly: fields visible and selectable, values never loading. Fixed by building the layer's fields via the provider API (`QgsField`/`addAttributes`/`updateFields`) instead, which sidesteps connection-string escaping entirely. Regression-tested directly (`tests/test_expression_builder.py`: a field name containing both `&` and `=`, confirmed to build a valid layer with a correctly matching schema and loadable values) and end-to-end through a real button click.

  **Visibility added regardless of root cause**: a new `values_status_label` under the values list reports every outcome explicitly - no sample layer could be built (with the real underlying error message), the selected field wasn't found in the sample schema, the load itself raised an exception (with its message), zero values found, or a plain count of distinct values loaded on success. Selecting a different field clears it. Also answers a question raised alongside the report ("we have to decide if it lists distinct values or all values"): `QgsVectorLayer.uniqueValues()` already deduplicates by design - both "Load some" and "Load all" have only ever shown distinct values, matching QGIS's own native expression builder convention; they differ only in how many distinct values are shown (a capped sample vs. every one), not in whether duplicates appear. 6 new/rewritten tests in `tests/test_expression_builder.py`, including one exercising the real `button.clicked` signal path directly (the existing tests all called `_load_all_values()`/`_load_sample_values()` directly, never actually simulating a click - a real "clicking does nothing" bug could in principle have lived entirely in the button-to-slot wiring, a gap this closes going forward even though the wiring itself checked out fine on inspection).

  Real end users were never actually affected by this specific gap: the real default `download_fn` (`gateways.atom.download`) happens to call `os.makedirs(dest_dir, exist_ok=True)` internally regardless, and `test_pipeline.py`'s own `test_download_items_places_files_using_item_subdirectory` had an equivalent `path.parent.mkdir(...)` baked directly into *its* fake - both incidentally masking the same missing guarantee from two different directions, until a widget-level test with a simpler, more faithful fake (matching what a real caller's contract should be, not what one specific implementation happens to also do) exposed it on a real QGIS install for the first time.

  Fixed at the actual source of truth: `download_items` now creates `dest_path.parent` (not just `central_repo`) immediately before calling `download_fn`, for every item, regardless of nesting depth - the directory-creation guarantee now belongs to the shared orchestrator, not to whichever `download_fn` happens to be plugged in. `test_pipeline.py`'s masking `mkdir` was removed from its own fake so that test now genuinely exercises this guarantee instead of quietly satisfying itself.

- **A second, adjacent "guessing from CSV columns" bug, same root cause as the geometry field one, surfaced immediately after that fix by getting past it**: "Illegal property name: BDTOPO_V3:FID for feature type BDTOPO_V3:itineraire_autre" - a QGIS-native error message (its own wording, not something this plugin constructs), triggered by "Add to map" on 17 selected rows.

  Traced to `guess_id_field` (`ui/wfs_widget.py`): `_ID_FIELD_NAMES` checked `"fid"` first, on the documented assumption that GeoServer's CSV output "consistently carrying a FID column" made it a reliable identifier. Real, but the wrong conclusion: that column is a synthetic pseudo-property (GeoServer automatically prepends the raw GML feature id to CSV output regardless of the feature type's own actual schema) - not necessarily a real, `CQL_FILTER`-filterable attribute. Confirmed directly against this exact feature type's real schema (the same live `DescribeFeatureType` fetch from two entries ago): it has no `"FID"` attribute at all, only `"cleabs"` ("clé absolue") - IGN's own real, confirmed cross-product unique-identifier convention, the very first field in that schema.

  Fixed by reordering `_ID_FIELD_NAMES` to check `"cleabs"` first. Deliberately **not** extended into the same DescribeFeatureType-validation architecture just built for the geometry field - noted honestly in `guess_id_field`'s own docstring as a real, known, deliberately-deferred gap rather than silently accepted: a feature type with neither `"cleabs"` nor any other real candidate as an actual schema attribute, but still carrying the synthetic CSV `"fid"` column, could hit this same failure class again for a different type. Worth building properly in a future pass if it recurs, not worth the added complexity speculatively right now for a single confirmed case.

- **A third real bug in the same "Add to map (N selected)" flow, found from a sharp question about where a BBOX clause in the actual request was coming from**: "why a bbox? the filter in the gui do the geometric query that results in multiple items being selected and that translated into a filtered layer." Correct observation - `build_id_list_filter` (SIGate's own code) produces only `cleabs IN (...)`, no BBOX at all. Traced the real source: QGIS's own native WFS provider automatically scopes every fetch to the current map canvas extent, and `build_wfs_uri`'s own `restrict_to_bbox` parameter (which controls this) already existed in the code - but the "Add to map (N selected)" call site never overrode its default (`True`), so an id-list selection was always getting an unnecessary, redundant BBOX combined into it via AND.

  This is wrong on two independent grounds, not just one: an id-list filter (`cleabs IN (...)`) is already a complete, canvas-independent selector, so adding a BBOX restriction on top is (1) semantically incorrect - a selected feature that's since scrolled out of the current view (an entirely normal thing to do between selecting rows and clicking Add) would be silently dropped from the result, even though it was explicitly selected by id - and (2) a real, confirmed contributor to request length for an already-long id list, plausibly the actual cause of the "empty response: Unknown error" failure reported two entries ago, though that wasn't independently re-confirmed this pass.

  Fixed: `_on_add_clicked` now passes `restrict_to_bbox=False` specifically when the id-list-filter branch is actually taken, leaving the default (`True`, canvas-restricted - correct for "add whatever's visible" when no specific selection was made) unchanged for every other case.

  Extended the existing `test_add_to_map_with_selected_rows_restricts_to_those_rows_by_id` test (which already covered this exact scenario) with the actual regression assertion, added a direct unit test for `build_wfs_uri`'s own `restrict_to_bbox` parameter, and added a confirming assertion to the no-selection case proving the default stays canvas-restricted there. 298 pure-Python tests pass, unaffected (Qt-dependent file).
