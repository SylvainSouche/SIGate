# SIGate — Candidate Source Reference

A working reference for national geodata services identified as potential SIGate sources, from a ~30-country survey (uploaded as `gis_resources_by_country.md` / `gis_gateways.csv`). Confidence markers below follow that survey's own convention: **Verified** (fetched/confirmed live), **Documented** (confirmed against current official docs, not live-fetched), **Unverified** (carried over, not independently checked). Where this project independently re-confirmed something via its own search, that's noted separately from the original survey's own confidence marker.

This document exists so the research itself isn't lost between sessions — every country the survey covered is listed here, not just the ones integrated so far.

---

## Integrated (in `sources/seed.py`)

Criteria applied: free, unauthenticated (no header/query-param key needed — this plugin's `AuthConfig` currently only supports `"none"` and a header-based apikey cleanly; a URL-embedded token or username/password doesn't fit either), and needing only gateway types this plugin already implements at the time of seeding (`wfs`, `wmts_wms`, `atom`, and — added later, once their own modules existed — `stac` and `geonorge_catalog`) — matching the same policy `sources/seed.py`'s own docstring already states for why a country isn't seeded until its needed gateway type exists.

| Source | Gateways added | Confidence |
|---|---|---|
| **IGN (France)** — `ign_fr` | Atom, WFS, WMTS (public + private/apikey), CSW (config-only, no gateway module yet) | Already fully verified and in production use since the start of this project. |
| **swisstopo (Switzerland)** — `swisstopo_ch` | WMTS, WFS, STAC (12 instances: swissALTI3D, swissTLM3D, swissSURFACE3D, SWISSIMAGE, plus 8 outdoor-activity route networks - ski touring, two snowshoe-route datasets, hiking/Wanderland, winter hiking, cycling/Veloland, mountain biking, skating - added in response to a direct request for outdoor-activity coverage) | WMTS independently re-confirmed this session against multiple official geo.admin.ch sources and a GitHub issue tracker. WFS URL is real (confirmed via an older community mailing-list post: "a few datasets are published via a WFS service") but the evidence is weaker than its WMTS sibling and describes limited coverage, not confirmed current — flagged in the config itself (`endpoint_confidence: weak_dated_reference_only`). Given Germany's own WFS guess (below) turned out to be wrong entirely, this one carries a real, similar risk that hasn't been ruled out. **STAC added in a later session**, once `gateways/stac.py` existed to back it: `data.geo.admin.ch`'s `/collections` and `/collections?provider=swisstopo` endpoints were fetched and confirmed live directly; a real STAC `/collections/{id}/items` response was not independently fetched the same way (STAC API's standard "next"-link pagination shape is implemented on the general spec + the confirmed `/collections` response's own `links` convention, not a captured live Items response). **One explicitly requested item deliberately NOT added**, checked directly and confirmed genuinely out of reach: SAC hut data - confirmed not an independent downloadable dataset at all, swisstopo's own Base Map documentation states this partner data is "neither entered nor managed by swisstopo." (Avalanche hazard-zone data *was* found and added, but on a different platform entirely - see `geodienste_ch` below, not this source.) |
| **Gefahrenkarten (geodienste.ch, Switzerland)** — `geodienste_ch` | WMTS, WFS, STAC | Added directly in response to a follow-up question ("no wms nor wfs layer with... identifies avalanche zone?"). A genuinely different Swiss platform from `data.geo.admin.ch` above - the *intercantonal* geodata portal, harmonizing cantonal data (here: hazard maps for avalanche/flood/landslide/rockfall, ~98% national coverage for avalanches specifically) under one shared schema/endpoint pattern, rather than swisstopo's federal platform. Confidence varies genuinely by gateway, not uniformly high: **WMTS is the best-confirmed** - this exact URL was fetched live and returned a complete, real WMS 1.3.0 GetCapabilities document, including confirmed avalanche-specific layer names (`gefahrenhinweisgebiet_lawine`, the legally-binding `gefahrengebiet_lawine`, and `intensitaet_lawine_*` by return period). **WFS required a real mid-session correction**: an external `services.csv` export listed `geodienste.ch/db/gefahrenkarten_v1_3_0/deu` as the WFS GetCapabilities URL, but fetching it directly with `SERVICE=WFS` returned WMS content regardless - the actual WFS endpoint (`wfs.geodienste.ch`, a different subdomain) was found inside the WMS document's own declared `<OnlineResource>` sibling link and confirmed live (real XML content-type response), though its exact FeatureType names weren't independently readable this session (the WFS tab discovers these live from GetCapabilities the same way it already does for every other WFS source, so this doesn't block the connection). **STAC is the weakest-confirmed**: the `{root}/collections/{id}/items` URL shape was inferred from one real, live-fetched per-canton STAC Item URL, not from an independently fetched Collection or Items-listing response. Deliberately NOT resolved this session: whether a live queryable geoservice exists for *historical* avalanche events specifically (SLF maintains avalanche accident/fatality records, but a geoservice for them wasn't found) or SLF's own live daily avalanche bulletin (confirmed real, but a separate API/protocol entirely, not this platform). |
| **Geonorge (Norway)** — `geonorge_no` | `geonorge_catalog` (a new gateway type, built specifically for this source) | Originally the concrete example this project used for "a source shape Bulk Listing's design doesn't fit at all" - `kartkatalog.geonorge.no/api/search` really is a flat search-and-facets API, not a browsable tree. That verdict turned out to be about the source's *native* shape, not a permanent limit on what could be built on top of it: `gateways/geonorge_catalog.py` derives a real two-level Theme→Dataset hierarchy from one CSV export of the whole catalog (confirmed live this session: `kartkatalog.geonorge.no/api/search?limit=10000&text=&mediatype=csv` returns all ~8,637 records as a flat semicolon-delimited CSV, including a per-row "Atom-feed" column). Level 1 is every Topic with at least one row carrying a real Atom feed URL; Level 2 is those rows themselves. The moment a Level 2 entry's own Atom feed URL is reached, this module delegates entirely to `gateways/atom.py` - no new download, pagination, or checksum logic was written, since a Geonorge dataset's Atom feed is a real, standard INSPIRE feed, structurally the same shape IGN's already are. Real, stated limitation: only 398 of the catalog's ~8,637 records carry an Atom feed at all (~5%) - everything else (WMS/WFS-only services, REST APIs) simply doesn't appear in this connection. The Level 1 theme list is curated from Topic values actually seen live this session (Basis geodata, Natur, Samfunnssikkerhet, Kyst og fiskeri, Høydedata, Geologi, Landbruk, Eiendom, Plan, Kulturminner, Transport, Forurensning, Energi, Befolkning) rather than dynamically enumerated - Geonorge's backend is Apache Solr (confirmed via its own public GitHub repo), which typically can return facet-value counts directly, but that shape wasn't confirmed in an actual fetched response this session. |
| **BKG TopPlusOpen (Germany)** — `bkg_de` | WMTS, WFS | WMTS independently re-confirmed this session against BKG's own PDF product documentation (English and German editions) and its MIS metadata catalog entry. **WFS was reported empty in real use and found to be a genuine bug**: BKG has no single unified WFS the way IGN does — its WFS offering is fragmented per dataset (`wfs_vg250`, `wfs_vg1000`, `wfs_gnde`, `wfs_vertriebseinheiten`, ...), the same "many endpoints, not one" pattern already identified below for Belgium/Slovakia/Ireland. The original config guessed a generic `.../wfs` URL that never corresponded to any real BKG service. Fixed to one specific, confirmed dataset: VG250 (Verwaltungsgebiete 1:250 000 — administrative boundaries, state through municipality level), confirmed via multiple independent BKG/MIS metadata-catalog sources, free, no access restrictions. This represents *one dataset*, not "Germany's WFS" generally — other BKG WFS datasets exist at their own separate endpoints, not seeded here. |
| **PDOK (Netherlands)** — `pdok_nl` | WMTS only | WMTS (BRT Achtergrondkaart) independently re-confirmed this session against multiple official pdok.nl pages. **Atom deliberately not added**: `pdok.nl/en/products/pdok-downloads/atomfeeds` is an HTML landing page listing many separate per-dataset feed URLs, not one machine-readable capabilities document the way IGN's own Atom gateway (one root URL covering every product) is — this plugin's `atom` gateway type and Bulk Listing tab currently assume the latter shape. Wiring PDOK's downloads in properly needs either picking one specific dataset's real feed URL as its own source, or extending the gateway/UI to handle "one source, many independent feeds" — neither decided yet. |
| **basemap.at (Austria)** — `basemap_at` | WMTS only | Confirmed to an unusually high degree for this project's own standard: one search result's own source URL was this exact endpoint, and the content returned was the real capabilities document itself (real layer identifiers, bounding boxes, explicit `"none"` auth, City of Vienna contact details) — independently corroborated by `geoland.at`'s own official nationwide-geoservices page describing the same URL and the same real layer names. No WFS found in the source research — WMTS-only. |

Five gateway modules now back these sources (`wfs`, `wmts_wms`, `atom`, `stac`, `geonorge_catalog`). The original four newly-added sources from the first pass (swisstopo's WMTS/WFS, BKG, PDOK, basemap.at) were never live-fetched from this environment (the sandbox this project's automated tests run in has no route to any of these domains) — confirmation there means independently re-checked via web search against multiple current official sources, not a live HTTP round-trip. Several additions made in later sessions *were* fetched live directly (swisstopo's and geodienste.ch's STAC/WMTS endpoints, and Geonorge's CSV export) - the source's own entry above says which, rather than this summary line asserting one blanket confidence level for everything in the table. Test before relying on any of these for anything beyond what this project's own tests already cover.

## Deferred — auth doesn't fit this plugin's current `AuthConfig` shapes

`AuthConfig.kind` currently supports `"none"` and `"apikey_header"` (a credential sent as an HTTP header) cleanly; a credential embedded directly in the URL's own query string is architecturally different and not yet handled anywhere in this plugin.

| Source | Type | Why deferred |
|---|---|---|
| **China (Tianditu / NGCC)** | WMTS | Requires a `tk=` token as a literal URL query parameter (mandatory since 2019); no free/shared key exists — each user needs their own registered developer key (10,000 req/day quota). |
| **Denmark (SDFI / Dataforsyningen)** | WMTS | Requires `username=`/`password=` as literal URL query parameters (free registered account via dataforsyningen.dk). Additionally, SDFI's own documentation states this specific WMTS route is scheduled for retirement 2027-01-15 — actively a bad time to build new tooling against it; check `confluence.sdfi.dk` for its replacement first. A separate, more modern token-auth WMS family also exists at `api.dataforsyningen.dk`, not evaluated here. |
| **Sweden (Lantmäteriet)** | WMTS | Requires a free "Geotorget" subscription/API key; the exact credential-delivery mechanism (header vs. query param) wasn't confirmed in the original survey. |

## Deferred — no single machine-readable endpoint (fragmented or fully gated)

| Source | Situation |
|---|---|
| **Ireland (Tailte Éireann / GeoHive)** | The detailed national basemap (MapGenie) is access-gated behind institutional login (e.g. universities), not a public anonymous service at all. The open alternative, GeoHive, is an ArcGIS Hub aggregating dozens of independent public-sector datasets, each with its own per-dataset endpoint — there is no single national WFS/WMTS to seed as one source. Revisit once/if a "browse a catalog, pick a dataset" mechanism exists (see `docs/spec.md` §3's CSW-router open item — GeoHive is structurally the same kind of problem). |
| **Belgium** | Federated, not unified: a federal service (NGI/IGN, `cartoweb.wmts.ngi.be` — real layer names `topo`/`topo-grey`/`overlay`/`crossborder`, confirmed against NGI's own CartoWeb.be v2021.04 product spec) covers the whole country, but Flanders (Digitaal Vlaanderen/Geopunt), Wallonia, and Brussels (IRISnet) each run their own separate, per-dataset regional services on top of that. The federal WMTS alone is a legitimate, clean candidate for later integration (free, simple, standards-compliant) — deferred here only for lack of time in this pass, not any architectural blocker. |
| **Slovakia (ÚGKK SR, ZBGIS)** | The original survey source pointed at a forestry university's own server (mismatched authority), corrected to the real ÚGKK SR endpoint (`zbgisws.skgeodesy.sk`) — a legitimate free WMTS, similarly just not yet added in this pass. WMS is split into many per-theme endpoints rather than one unified service, which would need its own decision if that's ever wanted too. |

## Deferred — protocol doesn't fit this plugin's gateway types

| Source | Situation |
|---|---|
| **Japan (GSI)** | No real WMTS at all. GSI's own documentation states plain XYZ tiles (`cyberjapandata.gsi.go.jp/xyz/{layer}/{z}/{x}/{y}.png`) are the actual, current, and only officially supported access method — WMS is explicitly called legacy in GSI's own docs. Two unofficial community WMTS wrappers exist (one of which, per its own maintainer's notes, hasn't had its underlying data updated since October 2023) but neither is official. Would need a new "XYZ tile" gateway type to integrate properly rather than fitting into `wmts_wms` as-is. |
| **Austria (BEV, "Karte" topographic map)** | Asked about directly (`maps.bev.gv.at/tiles/karte/{z}/{x}/{y}.png`) as an alternative to `basemap.at`'s styling. A genuinely separate BEV product (not the same map as `basemap.at`, which BEV only co-contributes to) — confirmed via a real community thread whose author directly checked BEV's own data catalog: BEV does have a WMTS for this map, but it's bound to an internal-only IP address (`10.1.33.203`), never publicly reachable. Publicly, it's XYZ tiles only, the same class of gap as Japan's GSI above - needs the same not-yet-built "XYZ tile" gateway type, not a config fix. |
| **Austria (BEV) INSPIRE view services generally** | A second, independent reason BEV's own services (as opposed to `basemap.at`, already integrated) don't fit this project's "mature, low-friction" tier: access requires a genuinely manual, form-based provisioning process, not self-service registration - confirmed directly from BEV's own documentation. Download an order form (PDF) from the BEV Portal → submit it to BEV's customer service by email/post → BEV sends an activation link → BEV sends a username/password for their "BEV-Interceptor" access-management system → generate a token via the Interceptor → append that token to actual WMS requests. No self-service "Register" flow exists for this specific product line, even though BEV's general customer portal does have one for other purposes - that's why one search for a registration link on the INSPIRE service pages specifically won't find anything. Every dataset in BEV's INSPIRE catalog (administrative boundaries, orthophoto, coordinate reference points, etc.) states "Anmeldung erforderlich" with this same process. Free of charge, but not something this plugin's current `AuthConfig` model or any automated flow could provision - would need a manual, once-per-user credential exchange outside the plugin entirely, then a token-based auth kind this project doesn't have yet (closer to Denmark/China's URL-embedded-credential situation than a simple header key). |

## Structural lessons worth remembering for future source additions

(Condensed from the original survey's own analysis, since these patterns are likely to recur.)

- **Domain migrations are the single biggest cause of a source going stale**, not the service disappearing outright — France (Géoportail → Géoplateforme), the Netherlands (`nationaalgeoregister.nl` → `service.pdok.nl`), and Denmark (Kortforsyningen → Dataforsyningen/SDFI) all did this. Worth periodically re-checking any seeded source's URLs still resolve, especially ones already known to have migrated once.
- **An endpoint returning nothing isn't automatically dead** — several "Invalid" entries in the original survey turned out to be an authentication wall (Sweden, China, Denmark's newer stack) rather than a broken URL. Worth distinguishing before assuming a source needs replacing rather than just an `AuthConfig`.
- **"One country, one geoportal" is often wrong.** Belgium and Ireland both turned out to be federated/fragmented rather than having one unified endpoint — worth checking for this pattern specifically before assuming a single source config can represent a whole country.
- **A mismatch between a source's stated authority and its actual URL is a real signal worth investigating**, not just sloppy data entry — it correctly pointed to genuine problems in Belgium (federal URL, regional metadata), Slovakia (a forestry university's server, mislabeled as the national cadastral authority), and Ireland (a heritage-monuments viewer, mislabeled as general topographic mapping) in the original survey.
